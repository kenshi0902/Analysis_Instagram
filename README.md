# Analysis_Instagram

Instagram のインサイトを Instagram Graph API から Google Apps Script(GAS)で自動取得し、Google スプレッドシートに蓄積して、GAS ウェブアプリのダッシュボードで分析するための仕組みです。

この README は、読む人に合わせて3部構成にしています。

| 章 | 対象 | 内容 |
|---|---|---|
| [1. 利用者向け](#1-利用者向け) | ダッシュボードで運用を振り返るメンバー | 開き方、画面の見方、数値を読むときのルール |
| [2. 管理者向け](#2-管理者向け) | GAS・トークン・トリガーを管理する人 | セットアップ、定期実行、更新・デプロイ、トラブル対応 |
| [3. 設計内容](#3-設計内容) | コードを修正・拡張する人 | 構成、データの流れ、シート設計、API の制約と対処 |

## 1. 利用者向け

### 1-1. ダッシュボードの開き方

- ダッシュボードは GAS のウェブアプリです。URL は管理者から共有されます。
- 閲覧できるのは、デプロイのアクセス設定で許可された Google アカウントだけです。開けない場合は管理者に連絡してください。
- 開いた直後は「読み込み中…」と表示され、スプレッドシートの読み込みが終わると表示されます。
- 画面上部の「最終取得」で、データの種類ごとに最後に取得した日時を確認できます。古いままの場合は管理者に連絡してください。

詳しい見方と分析の進め方は、Notion の説明書ページ(DataBase Wiki / 開発 / Instagram API /「Instagram ダッシュボード 説明書」)にまとめています。要点だけなら [docs/dashboard-guide.md](docs/dashboard-guide.md) を参照してください。

### 1-2. 画面の構成

| タブ | わかること | 主な表示 |
|---|---|---|
| 概要 | アカウント全体のリーチ・反応・フォロワー獲得が、前の期間より良くなったか | KPI(期間リーチ・リーチ率・シェア率など)、推移グラフ(日・週・月)、フォロワー獲得ファネル |
| 投稿(フィード・リール) | どの投稿が広く届き、反応されたか | リーチ × ER の散布図、投稿ごとのリーチ率、曜日 × 時間帯ヒートマップ、投稿一覧 |
| ストーリーズ | 何枚目で見られなくなっているか、投稿から何時間で見られているか | 「日別シーケンス」: 残存率、位置別の離脱率、日ごとの完走率、タップ操作の構成比 / 「投稿からの時間推移」: 到達曲線、1時間ごとの新規リーチ、ストーリー別の推移と平常ペースの比較、投稿時刻別の6時間後リーチ。「対象」でストーリーを1枚選ぶと、ストーリーの画像とともに、KPI・到達曲線・新規リーチがそのストーリー単体の値と平常比に切り替わる |
| オーディエンス | どの層に届き、どの層が反応しているか | 年齢層・性別・都市・国の構成比、反応指数 |

- 期間は 7日 / 30日 / 90日 / 全期間 から選べます。前期間比は「同じ長さの直前の期間」との比較です。
- 表は列名をクリックすると並べ替えできます。グラフにマウスを乗せると詳細が出ます。
- 最重要KPIは**リーチ拡大**です。青枠のKPIカード(期間リーチ・リーチ率・シェア率)を最初に確認してください。

### 1-3. 数値を読むときのルール

| ルール | 理由 |
|---|---|
| 投稿・ストーリーは実数ではなく「÷リーチ」の率で比べる | フォロワー数や投稿の古さに左右されず、投稿の質を比べられる |
| 代表値は中央値。件数 n が5未満の値は薄く表示される | 1本のバズで平均が歪むのを防ぐ。n が少ない値は参考値 |
| 率の前期間比は pt 差、実数の前期間比は変化率 | 例: ER 5.0% → 5.5% は「+0.5pt」 |
| 投稿どうしは「投稿後7日」など経過日数を揃えて比べる | 投稿の数値は日が経つほど増えるため |
| フォロワー数の点線は推定値、投稿の「集計中」は投稿後7日未満 | 確定値と混同しないため |

### 1-4. 主な指標

| 指標 | 計算式 | 見方 |
|---|---|---|
| リーチ率 | リーチ ÷ フォロワー数 | フォロワー規模に対してどれだけ広く届いたか(100%超もありうる) |
| シェア率 | シェア ÷ リーチ | フォロワー外への拡散力の目安 |
| ER(リーチ基準) | インタラクション合計 ÷ リーチ | 投稿の質の評価に使う |
| ER(フォロワー基準) | インタラクション合計 ÷ フォロワー数 | 外部の業界平均と比べるときに使う |
| 保存率 | 保存 ÷ リーチ | 有益性の目安 |
| プロフィール訪問率 / フォロー転換率 | 訪問 ÷ リーチ / フォロー ÷ 訪問 | フォロワー獲得のどこで落ちているか |
| 完走率(ストーリーズ) | その日の最後のリーチ ÷ 1枚目のリーチ | 1日のストーリー構成の評価 |
| 反応指数(オーディエンス) | 各層の構成比 ÷ フォロワーの構成比 | 1.2以上はよく反応している層 |
| 50%到達時間(ストーリーズ) | 最終リーチの半分に達するまでの時間 | 短いほど投稿直後に見られている。投稿時刻の判断に使う |
| 6時間後の到達率(ストーリーズ) | 6時間後のリーチ ÷ 最終リーチ | 見られるタイミングの偏り |

### 1-5. スプレッドシートについて

- API で取得した数値は、`API_` で始まるタブと「ストーリーズインサイト」「フォロワー数」タブに自動で書き込まれます。**これらのタブの数値は手で書き換えないでください**(次回の取得で上書きされます)。
- 手入力のタブ(内容・意図・振り返り・改善などの運用メモ、DM、フォロー活動、ストーリーネタ帳など)は、これまでどおり手で記入します。スクリプトはこれらに触れません。
- 自動取得するタブに手入力用の列を追加しても構いません。スクリプトが管理する列以外は上書きされません。

## 2. 管理者向け

### 2-1. 前提条件

- Instagram アカウントがビジネスまたはクリエイターアカウントで、Facebook ページと連携していること
- Meta for Developers のアプリで Instagram Graph API を有効化し、`instagram_basic`・`instagram_manage_insights`・`pages_show_list`・`pages_read_engagement` の権限を持つアクセストークンを発行していること
- オーディエンス属性の取得には、フォロワーが100人以上必要

### 2-2. 認証情報

アクセストークンなどはコードに書かず、GAS の「プロジェクトの設定」→「スクリプト プロパティ」に登録します(Git 管理外)。

| キー | 必須 | 内容 |
|---|---|---|
| `IG_ACCESS_TOKEN` | ○ | 長期アクセストークン |
| `IG_USER_ID` | ○ | Instagram ビジネスアカウント ID |
| `SPREADSHEET_ID` | ○ | 書き込み先スプレッドシートの ID |
| `IG_API_HOST` | | 既定 `graph.facebook.com`。Instagram ログインなら `graph.instagram.com` |
| `IG_API_VERSION` | | 既定 `v23.0` |
| `STORY_IMAGE_FOLDER_ID` | | ストーリー画像の保存先フォルダ。未設定なら初回の保存時にマイドライブ直下へ「Instagram_ストーリー画像」を作成して自動で記録する |

> [!WARNING]
> アクセストークンを Notion・チャット・スプレッドシートなどに平文で貼らないでください。共有範囲の人が誰でもアカウントのデータを取得できてしまいます。漏れた場合は Meta 側で無効化して再発行してください。

### 2-3. 初回セットアップ

```bash
clasp push   # src/ を GAS に反映(scriptId は .clasp.json、Git 管理外)
```

GAS エディタで、次の関数を上から順に手動実行します。

1. `checkConfig`: スクリプトプロパティが揃っているか確認
2. `testConnection`: API に接続できるか確認(ユーザー名・フォロワー数を表示)。失敗したら `diagnose` で原因を切り分ける
3. `initSheets`: 書き込み先のタブと見出し行を作成
4. `runBackfill`: 過去分をまとめて取得(投稿は全件、アカウント日次は30日分、期間ユニーク値は26週・6か月分)。投稿数が多いと数分かかる
5. ウェブアプリとしてデプロイ: 「デプロイ」→「新しいデプロイ」→「ウェブアプリ」(実行ユーザー: 自分 / アクセス: 自分のみ)
6. `installTriggers`: 定期実行を登録(何度実行しても重複しない)

### 2-4. 定期実行

| 関数 | 頻度 | 内容 |
|---|---|---|
| `syncStories` | 1時間おき | ストーリーの最新インサイトで更新し、実行ごとの値を時間推移として追記(間隔は `stories.gs` の `STORY_SYNC_MINUTES`)。新しいストーリーの画像をドライブに保存 |
| `syncFollowers` | 毎日 1時台 | フォロワー数・フォロー数・投稿数の実測値を記録 |
| `syncMedia` | 6時間おき | 直近30日の投稿を更新し、投稿後1/7/28日時点のスナップショットを記録 |
| `syncAccountAll` | 毎日 2時台 | アカウント日次 → 期間ユニーク値(直近7/30日・週・月) → フォロワー数の推定値補完 の順に実行 |
| `syncAudience` | 毎週月曜 2時台 | オーディエンス属性の最新値で更新 |
| `refreshToken` | 毎週月曜 3時台 | トークン更新(Instagram ログインのみ。Facebook ログインはスキップ) |

実行結果は GAS エディタの「実行数」で確認できます。

### 2-5. 手動で実行できる関数

| 関数 | 用途 |
|---|---|
| `runAll` | 定期実行の処理を一度にすべて実行 |
| `runBackfill` | 初回用。過去分をまとめて取得 |
| `syncMediaBackfill` | 全期間の投稿を取り直す |
| `syncAccountBackfill` | アカウント日次を30日分取り直す |
| `syncAccountPeriodsBackfill` | 期間ユニーク値を26週・6か月分取り直す |
| `backfillFollowers` | フォロワー数の過去分を純増から逆算して補完(実測の行は上書きしない) |
| `removeTriggers` | このプロジェクトの定期実行トリガーを削除 |

### 2-6. コードの更新とデプロイ

1. `main` から作業ブランチを切って修正し、マージする
2. `clasp push` で GAS に反映する
3. トリガー構成を変えた場合は `installTriggers` を再実行する
4. 「デプロイを管理」→ 既存のウェブアプリの鉛筆アイコン → 新しいバージョンを作成する(URL は変わらない)

ウェブアプリはデプロイした時点のコードで動くため、手順4を忘れると画面に反映されません。

### 2-7. アクセス設定

- 現在のアクセス設定は「自分のみ」です。ほかのメンバーに見せる場合は「デプロイを管理」でアクセスを変更します。
- 実行ユーザーを「自分」のままにすると、閲覧者はスプレッドシートの権限なしでダッシュボードを見られます。その分、URL を知っている対象者は全データを閲覧できるため、範囲は慎重に決めてください。

### 2-8. トラブル対応

| 症状 | 原因と対処 |
|---|---|
| 「最終取得」が古い | 「実行数」でエラーを確認。トークン切れなら再発行してスクリプトプロパティを更新 |
| `runBackfill` などがタイムアウト(6分超) | 投稿数が多いため。`runBackfill` の代わりに、各関数(`syncMediaBackfill` など)を1つずつ実行する。投稿の書き込みは処理の最後にまとめて行うため、`syncMediaBackfill` 単体でも6分を超える場合は分割実行の仕組みが必要(再実行しても重複はしない) |
| 「まとめ取得に失敗、個別取得に切り替え」の警告 | 一部の指標がその投稿で未対応。取れる指標は取得済み。未対応と判明した指標は同じ実行内で以降の投稿から除外される |
| オーディエンスで `timeframe` のエラー | API v20 以降は `this_week` / `this_month` のみ有効。`account.gs` の指定を確認 |
| フォロワー数の補完が「追加 0」 | `API_アカウント日次` の「フォロワー純増」が空か、直近の純増が API 側でまだ反映されていない。翌日以降の `syncAccountAll` で自動的に補完される |
| ダッシュボードの「期間リーチ」が「–」 | `syncAccountPeriodsBackfill` が未実行 |

### 2-9. 開発ルール

- ブランチ運用: `main` から作業ブランチを切り、変更後にマージする
- コミット前に `git status` と差分を確認し、トークン・ウェブアプリの URL・取得データが含まれていないことを確かめる
- `.gitignore` は `*.json` を除外し、`src/appsscript.json` のみ例外としている。`.clasp.json`(scriptId)と `.clasprc.json`(clasp の認証情報)は Git 管理外

## 3. 設計内容

### 3-1. 目的と方針

- 手入力しているインサイト数値の転記作業をなくし、取りこぼしを防ぐ(特にストーリーズは投稿から24時間で取得できなくなる)
- 人が書く欄(内容・意図・振り返りなど)は手入力のまま残し、スクリプトは数値だけを扱う
- ダッシュボードは「数値を並べる」ことより「公平に比べられる」ことを優先する(背景と決定事項は [docs/dashboard-redesign.md](docs/dashboard-redesign.md))

### 3-2. 全体構成

```
Instagram Graph API
        │  UrlFetchApp(リトライ・ページネーション)
        ▼
GAS 取得処理(時間主導型トリガー)
        │  upsert(キー列で突き合わせ、管理列のみ書き込み)
        ▼
Google スプレッドシート(API_ タブなど)
        │  getDashboardData()
        ▼
GAS ウェブアプリ(Index.html + Chart.js)で集計・可視化
```

| 項目 | 内容 |
|---|---|
| 実行基盤 | Google Apps Script(単体スクリプト。出力先は `SpreadsheetApp.openById` で指定) |
| データ取得元 | Instagram Graph API(既定 `graph.facebook.com` / `v23.0`) |
| 保存先 | Google スプレッドシート |
| 可視化 | GAS ウェブアプリ(HtmlService)+ Chart.js 4.4.1 |
| ソース管理 | Git + [clasp](https://github.com/google/clasp)(`rootDir: src`) |

### 3-3. ディレクトリ構成

```
Analysis_Instagram/
├── README.md
├── .gitignore
├── docs/
│   ├── dashboard-redesign.md  # ダッシュボード再構築の提案と決定事項
│   └── dashboard-guide.md     # ダッシュボードの見方(要約版)
└── src/
    ├── appsscript.json  # GAS マニフェスト(タイムゾーン Asia/Tokyo、ウェブアプリ設定)
    ├── config.gs        # 定数・テーブル(シート名・キー・管理列)定義・設定読み込み
    ├── api.gs           # Graph API 呼び出し・リトライ・ページネーション・インサイト解析
    ├── sheet.gs         # シート書き込み(ヘッダー名で列特定・upsert・手入力列の保護)
    ├── stories.gs       # ストーリーズのインサイト
    ├── followers.gs     # フォロワー数の日次記録と過去分の推定補完
    ├── media.gs         # フィード・リールのインサイトと投稿後1/7/28日のスナップショット
    ├── account.gs       # アカウント日次・期間ユニーク値・オーディエンス属性
    ├── refresh.gs       # トークン更新(Instagram ログインの場合のみ)
    ├── triggers.gs      # トリガーの登録・削除
    ├── main.gs          # 設定確認・接続テスト・シート初期化・一括実行
    ├── dashboard.gs     # ウェブアプリ(doGet)とシートデータの読み出し
    └── Index.html       # ダッシュボード画面
```

### 3-4. シート(テーブル)設計

`config.gs` の `TABLES` で定義しています。手入力の既存タブと混ざらないよう、新しく追加したデータは `API_` 接頭辞の専用タブに書き込みます。

| タブ | キー | 内容 | 書き込み元 |
|---|---|---|---|
| ストーリーズインサイト | ストーリーID | ストーリーごとの閲覧・リーチ・返信・シェア・タップ操作(最新値)、保存した画像のドライブのファイルID | `syncStories` |
| API_ストーリー推移 | ストーリーID\|経過分 | 実行ごとのストーリーの値(投稿からの時間推移)。ダッシュボードには投稿が直近90日の分だけ渡す | `syncStories` |
| フォロワー数 | 日付 | 日ごとのフォロワー数・フォロー数・投稿数・前日比・種別(実測/推定) | `syncFollowers` / `backfillFollowers` |
| API_フィード | メディアID | フィード投稿ごとの累計インサイト | `syncMedia` |
| API_リール | メディアID | リールごとの累計インサイト(平均・合計視聴時間を含む) | `syncMedia` |
| API_投稿推移 | メディアID\|経過日数 | 投稿後1・7・28日時点のインサイト | `syncMedia` |
| API_アカウント日次 | 日付 | アカウントの日次指標(リーチ・反応・プロフィール訪問・フォロー増減・純増) | `syncAccountDaily` |
| API_アカウント期間 | 期間キー | 期間のユニーク値(R7 / R7前 / R30 / R30前 / W\|月曜日付 / M\|年月) | `syncAccountPeriods` |
| API_オーディエンス | 対象\|区分\|項目 | 年齢層・性別・都市・国の人数(フォロワー / リーチ層 / エンゲージ層) | `syncAudience` |

#### 書き込みの仕様(`sheet.gs`)

- 列は見出し名で特定するため、列の並べ替えや手入力列の追加をしても壊れない
- `TABLES` の `headers` にある列だけ書き込み、それ以外の列(手入力列・数式列)には触れない
- キー列で突き合わせ、あれば更新・なければ追記(upsert)。キー列は文字列として保存する(18桁の ID が数値に丸められるのを防ぐ)
- 取得できなかった指標は空で上書きせず、既存の値を残す
- 派生指標(率など)はシートに書かず、ダッシュボード側で計算する

#### 既存の手入力シートとの関係

| 既存タブ | 扱い |
|---|---|
| アカウントインサイト月間・週間 | `API_アカウント日次` / `API_アカウント期間` / `API_オーディエンス` とダッシュボードで代替 |
| フィードインサイト / リールインサイト | 数値は `API_フィード` / `API_リール` で取得。運用メモ列は手入力のまま |
| dm / フォロー | Graph API の制約があるため手入力を維持 |
| ストーリーネタ帳 / インサイト改善チェックリスト | 手入力 |

### 3-5. 取得処理の設計

| 処理 | エンドポイント | 設計のポイント |
|---|---|---|
| 共通(`api.gs`) | — | レート制限系エラー(code 4/17/32/613)と 5xx は指数バックオフで最大4回リトライ。`paging.next` を最大20ページまで追跡。エラーメッセージにトークンを含めない |
| インサイト取得 | `/{media-id}/insights` | 指標をまとめて取得し、失敗したら1指標ずつ取り直す。指標名が原因のエラーは「その種類のメディアでは未対応」と記録し、同じ実行内で以降の投稿から除外(実行時間の膨張を防ぐ) |
| 投稿 | `/{ig-user-id}/media` | 通常は直近30日分だけ更新。投稿後 1/7/28日(+24時間以内)に初めて取れた値をスナップショットとして記録し、以後は上書きしない |
| アカウント日次 | `/{ig-user-id}/insights`(`metric_type=total_value`) | JST の日付境界で1日ずつ取得。`follower_count` は時系列で取得し、`end_time` の前日に割り当てる |
| 期間ユニーク値 | 同上(`since` / `until` で期間指定) | リーチ・エンゲージしたアカウントは日次を足すと重複するため、期間ごとに取得。API 上限(30日)を超える月は末尾30日で近似し「近似」と記録 |
| フォロワー数 | `/{ig-user-id}?fields=followers_count` | API は過去の値を返さないため毎日記録。開始前の分は「前日の値 = その日の値 − 前日の純増」で逆算し「推定」と記録。実測の行は上書きしない |
| オーディエンス | `/{ig-user-id}/insights`(`breakdown`) | フォロワーは `period=lifetime`、リーチ層・エンゲージ層は `timeframe=this_month` |

### 3-6. ダッシュボードの設計

- `getDashboardData()` が `TABLES` の全タブを読み、ブラウザ側(`Index.html`)で集計する。シートには生の値だけを持つ
- 比較のルール
  - 投稿・ストーリーは「÷リーチ」の率で比べ、代表値は中央値。n を併記し、n<5 は薄く表示
  - KPI には同じ長さの直前の期間との差を付ける(率は pt 差、実数は変化率)
  - リーチは期間ユニーク値を使う。7日・30日は `R7` / `R30`、90日・全期間は確定済みの週ユニークの平均
  - 投稿は評価時点(投稿後1/7/28日・現在)を揃えて比べる。「現在」では投稿後7日未満を集計中として中央値から除外
  - 投稿のリーチ率は、投稿日のフォロワー数の記録がある投稿だけで計算する(範囲外を近似すると歪むため)
- 決定事項(2026-11-14): ER はリーチ基準を主・フォロワー基準を併記。最重要KPIはリーチ拡大(先頭KPIは期間リーチ・リーチ率・シェア率、投稿一覧はリーチ率順)
- 配色は検証済みのカテゴリカルパレット(最大4色)を固定順で使い、ライト/ダークの両モードに対応

### 3-7. API の制約と対処

| 制約 | 対処 |
|---|---|
| ストーリーは投稿から24時間で取得できなくなる | 1時間おきに取得し、実行ごとの値を推移として残す |
| ストーリーの `media_url` は期限付きで、公開終了後は取り直せない | 公開中に画像(動画はサムネイル)を1回だけドライブへ保存し、ファイルIDをシートに記録 |
| フォロワー数の過去の値は取得できない | 毎日記録し、開始前は純増から推定 |
| `follower_count`(純増)は直近1〜2日の反映が遅れる | 遅れている日は純増0と仮定し、翌日以降の補完で更新 |
| 期間指定は1回30日まで | 直近7/30日・週・月の単位で取得。30日超の月は近似 |
| オーディエンスの `last_30_days` 等は v20 で廃止 | `this_month` を使用 |
| オーディエンス属性はフォロワー100人以上が条件 | 取得できない場合は画面に案内を表示 |
| GAS の1回の実行は最大6分 | 通常は直近30日の投稿のみ更新。未対応の指標を除外して呼び出し回数を抑える。全期間のバックフィルは投稿数が非常に多いと超える可能性がある(現状は分割実行に未対応) |
| 投稿の種類によって取得できない指標がある | 取れる指標だけ書き込み、未対応の指標は以降除外 |

#### ストーリーの収集周期

時間単位の分析には、最新値の上書きではなく実行ごとの履歴が必要です。周期は次の比較から1時間を既定にしています(ストーリー10件が同時に公開中の場合の目安)。

| 周期 | API 呼び出し | GAS 実行時間/日 | 推移の行数/年 | 評価 |
|---|---|---|---|---|
| 6時間 | 21回/6h | 約1分 | — | 推移が4点しかなく分析できない |
| **1時間(既定)** | 21回/h | 約4分 | 約4.4万行 | 24点の推移が取れ、Meta の上限(約200回/h)・GAS の上限(90分/日)に余裕がある |
| 30分 | 42回/h | 約8分 | 約8.8万行 | 投稿直後が細かく見えるが、シートの読み込みが重くなる |
| 15分 | 84回/h | 約16分 | 約17.5万行 | 他の取得処理と重なると API 上限に近づく |

- 取得時刻はストーリーごとにずれるため、ダッシュボードでは前後の取得値を直線補間して「投稿後◯時間」の値を求める(投稿時点は0とみなす)
- 最後の取得が投稿後20時間以降のストーリーを「完了」とし、到達曲線や中央値に使う
- 周期を変える場合は `STORY_SYNC_MINUTES`(1 / 5 / 10 / 15 / 30 / 60)を変更して `installTriggers` を再実行する
- `API_ストーリー推移` は行が増え続けるため、数年運用して読み込みが遅くなったら古い行を別シートへ退避する

#### ストーリー画像の扱い

- 保存は `syncStories` の中で、まだ画像ファイルIDのないストーリーに対して1回だけ行う。取得に失敗しても取得処理は止めず、次回の実行で再試行する
- ダッシュボードは、個別表示で選んだストーリーの画像だけを `getStoryImage()` で data URL として読み込む(全件を一度に送ると重いため)
- ウェブアプリはオーナー権限で動くため、`getStoryImage()` は保存フォルダ内のファイルだけを返す。任意のファイルIDを渡されても、オーナーのドライブ上の他のファイルは読めない
- ドライブへの書き込みのため、導入時に権限の再承認が必要。容量の目安は1枚100〜300KB(1日5枚で年0.2〜0.5GB)
